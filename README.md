# cs5336-project

React + Vite frontend for the airport luggage tracking system. Talks to the [cs5336-backend](../cs5336-backend) Express API.

The application models a single airport handling departures: passengers check in with bags, ground staff move bags through security to the gate, gate staff board passengers and notify admin when a flight is ready for departure, and admins manage flights, passengers, and staff.

## Tech stack

- Vite 5 + React 18 (mostly JSX, some TypeScript)
- shadcn/ui + Tailwind CSS + Radix primitives
- React Router 6 for routing, with role-guarded routes
- React Query (set up but minimally used)
- date-fns, lucide-react, sonner toasts, react-hook-form + zod

## Prerequisites

- Node.js 18+
- A running [cs5336-backend](../cs5336-backend) on `http://localhost:3001` (defaults match)

## Setup

### 1. Install

```sh
cd cs5336-project
npm install
```

### 2. Create `.env` (optional)

`.env` is gitignored. The frontend defaults to `http://localhost:3001/api` if `VITE_API_URL` is not set, so for a local-only run you don't strictly need an `.env`. Create one only if your backend lives elsewhere:

```
VITE_API_URL=http://localhost:3001/api
```

A Supabase client is also wired up at [src/integrations/supabase/client.ts](src/integrations/supabase/client.ts), but **no application code currently uses it** — all data flows through `VITE_API_URL` to the Express backend, which talks to Supabase on your behalf. You can ignore the `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` variables; the client will be created with `undefined` values and is never invoked.

### 3. Run the dev server

```sh
npm run dev
```

App opens at `http://localhost:5173`. Login page is at `/login`; everything else requires a valid JWT.

|---|---|---|
| Administrator | `admin` | `Admin123` |
| Airline / Gate / Ground staff | (auto-generated by the seed) | (auto-generated, captured on the first seed run) |

The 28 real staff members come from the spreadsheet (9 airline + 9 gate + 10 ground). Their usernames are `lastname + 2-digit` and passwords are random — capture them from the seed script's first-run output.

Passenger logins use a 6-digit identification + 10-digit ticket number. The seed leaves 120 passengers in your Supabase `passenger` table with the statuses from the spreadsheet (45 checked-in, 52 not-checked-in, 23 boarded). Use any `(identification, ticket_number)` pair as the passenger login.

## Roles & flows

### Administrator (`/admin`)

- **Flights Management** — add flights (validates 2-letter airline code, 4-digit flight number, unique gate per terminal), view passenger manifests, remove flights (cascades to passengers and bags).
- **Passengers Management** — add passengers to a flight, search/filter/paginate, remove (cascades to bags).
- **Staff Management** — add staff per role; the admin's email client opens with a `mailto:` containing the generated username + plaintext password.
- **Messages** — admin board: receives departure-ready notifications and remove-passenger requests, with action buttons to remove flights/passengers.

### Airline Staff (`/airline-staff`)

- **Check-In** — search passenger by ticket, verify they're on this airline and not already checked in, attach 0–10 bags with counter numbers, submit check-in, optionally report a security issue (which removes the bags and notifies admin).
- **Bags Management** — list bags filtered by location, view location history, report security violations.
- **My Flights** — overview of this airline's flights with check-in/boarded counts.
- **Messages** — airline message board; receives security-violation alerts from ground staff with one-click "remove bags & notify admin" actions.

### Gate Staff (`/gate-staff`)

- **Gate selection** — at start of shift, pick one of this airline's gates (you work one gate at a time).
- **Boarding** — passenger manifest for the selected flight, search passenger by ticket, verify all bags are at the gate, board the passenger, notify admin when everyone is boarded and all bags are loaded.
- **Flights** — overview of all this airline's flights with status (ready/boarding/not ready). Can change a flight's gate, which writes to `flight_gate_history` and notifies ground staff via the ground board.
- **Messages** — gate message board.

### Ground Staff (`/ground-staff`)

- **Location selection** — at start of shift, pick *Security Clearance* OR a specific gate (different navigation menus for each).
- **Security Clearance** — list bags pending security; move check-in → security → gate, or report a violation (which marks the bag and posts to the airline message board).
- **Load Bags** (when at a gate) — list bags at this gate; load them onto the aircraft (only after the passenger has boarded).
- **Gate Bags** (when at a gate) — overview of all bags for this flight.
- **Messages** — ground message board.

### Passenger (`/passenger`)

Live dashboard showing the passenger's flight info and bag-tracking progress (check-in → security → gate → loaded), auto-refreshed every 30 seconds.

## How it works

- **All API calls** go through the `api.*` wrapper in [src/lib/api.js](src/lib/api.js), which adds `Authorization: Bearer <token>` to every request and handles JSON serialization.
- **Tokens** are stored in `sessionStorage` under key `airport_token`. On 401 the client clears the token and navigates to `/login`. Tokens expire silently after 24 hours.
- **Auth state** lives in [`AuthContext`](src/contexts/AuthContext.jsx). On mount, if a token exists, it calls `/auth/me` to restore the session. If `/me` fails, the token is cleared.
- **Application data** (flights, passengers, bags, staff, messages, issues) lives in [`DataContext`](src/contexts/DataContext.jsx). Loaded once on mount via `Promise.all`, mutated through context methods, auto-refreshed by some pages every 30 seconds.
- **Routing** in [App.jsx](src/App.jsx) uses React Router 6 nested routes with `<ProtectedRoute>` guards. A user logging in as `gate_staff` who tries to navigate to `/admin` is redirected back to `/gate-staff`.

## Things to know / current limitations

In the spirit of being honest about what works and what doesn't:

- **Race conditions in mutation handlers.** Several pages call async DataContext methods (`updateBagLocation`, `updatePassengerStatus`, `addMessage`) without `await`-ing them — see [Boarding.jsx:88](src/pages/gate-staff/Boarding.jsx), [GateStaffFlights.jsx:73](src/pages/gate-staff/GateStaffFlights.jsx), [airline-staff/Messages.jsx:67-81](src/pages/airline-staff/Messages.jsx), [SecurityClearance.jsx](src/pages/ground-staff/SecurityClearance.jsx). The toast fires before the network round-trip resolves; if a request fails, the user sees "success" anyway and local state is briefly wrong until the 30-second auto-refresh corrects it.
- **Tab-isolated tokens.** Tokens live in `sessionStorage`, not `localStorage`. Logging out of one tab doesn't sign you out of others. This is intentional — multiple roles can be open in different tabs for testing.
- **JWT expires silently at 24h.** The user is dropped to `/login` mid-action without a toast. The flow works but is jarring.
- **`gate01` and `ground01` see only AA flights.** This is a backend / schema constraint, not a frontend bug — `staff.airline_code` is `NOT NULL` in Supabase, so every staff member is pinned to one airline. Gate and ground staff aren't conceptually airline-scoped, but the schema forces it. Demo flows for multi-airline gate operations don't work cleanly.
- **`Index.jsx` is dead.** [src/pages/Index.jsx](src/pages/Index.jsx) renders an empty div. Routing in [App.jsx:47](src/App.jsx) redirects `/` → `/login` so it's never shown. Safe to delete.
- **Generated `supabase/types.ts` is dead and stale.** [src/integrations/supabase/types.ts](src/integrations/supabase/types.ts) declares `Tables: { [_ in never]: never }` — it was generated against an empty Supabase project. The frontend never imports it. Either regenerate it from the canonical `zolhcvlpskwwxblairbc` project or delete it.
- **`mailto:` for staff credentials** — when an admin adds a staff member, the browser opens a `mailto:` link with the generated password in the URL. The plaintext password ends up in the admin's browser history. Acceptable for a demo, not for production.
- **No optimistic updates with rollback** — the data context updates local state from the response of each mutation. If a request fails, local state stays in sync because the optimistic write happens *after* the await. But UI flows that don't await (see first bullet) bypass this.
- **30s polling refetches all 6 endpoints in parallel.** Fine for the seeded dataset (~250 rows total); would need pagination + targeted refresh for production.
